# SPEC：班级实训耗材智能管理系统 v1.1

## Problem Statement

班级实训课耗材（焊丝、砂纸、记号笔、电阻、实训导线等）目前靠纸质本子登记：库存余量不透明、领用无法追溯、临上课才发现缺料，班委人工统计费时且易漏记。需要一个轻量 Web 系统完成"登记—扣减—巡检—提醒—补货"的业务闭环，并用"规则引擎 + 大模型润色"的分级补货 Agent 辅助教师决策；同时满足赛事对 CodeArts CI/CD 流水线发布的硬性要求。

## Solution

基于 Vue 3 + FastAPI + MySQL 8.0 的班级实训耗材智能管理系统：

- 三角色（教师 / 班委 / 学生）登录与权限矩阵；班委可新增与启停学生账号
- 耗材档案（含安全库存线）、批量领用（最多 5 行、整单原子）、撤销红冲、库存总览预警、流水查询与 CSV 导出
- 智能补货 Agent：规则引擎输出紧急/一般/观察三级分级，DeepSeek 经适配层润色判断依据，3 秒超时降级为规则模板
- 建议处置即入库：录入实际入库数量即完成补货，全程操作日志可追溯
- CodeArts 三阶段流水线（前端构建 → pytest → 镜像构建发布）；云端单台 ECS + Docker Compose；本地裸机零 Docker 启动兜底

## User Stories

### 账号与权限
1. 作为实训教师，我想用账号密码登录并只看到教师菜单，以便专注查看库存与补货决策。
2. 作为班委/耗材管理员，我想登录后维护耗材档案与学生账号，以便承担日常管理。
3. 作为实训学生，我想登录后只能登记本人领用并查询本人记录，以便不越权访问他人数据。
4. 作为任一角色，我想在登录态 8 小时内免重复登录，以便课间快速操作。
5. 作为教师或班委，我想在越权调用接口时收到 403 提示，以便确认权限边界生效。
6. 作为班委，我想新增与启停学生账号，以便新生入班后能立即登记领用。
7. 作为班委，我想无法创建教师账号或修改任何角色，以便权限不被提权。

### 耗材档案
8. 作为班委，我想新增耗材（名称、规格、单位、存放位置、安全库存线、当前库存），以便完成建档。
9. 作为班委，我想修改耗材信息与安全库存线，以便随实际使用调整。
10. 作为班委，我想停用耗材并保留历史流水，以便不误删数据。
11. 作为班委，我想系统预置 5 类演示耗材与示例安全线，以便开箱演示。

### 领用与撤销
12. 作为学生，我想一次登记最多 5 行不同耗材，以便课间一次领完多种。
13. 作为教师或班委，我想为指定学生代登记领用，以便集中办理。
14. 作为领用人，我想补录过去 30 天内的领用且不能填未来时间（分钟级），以便补账。
15. 作为领用人，我想任一行库存不足时整单被拒绝并指出具体行，以便不产生半截账。
16. 作为教师或班委，我想撤销错误领用并填写原因，以便纠正错误且保留审计链。
17. 作为教师/班委，我想已撤销的流水不可再次撤销、红冲流水不可撤销，以便数据一致。
18. 作为学生，我想系统拒绝我执行撤销操作，以便职责边界清晰。

### 库存与查询
19. 作为任一角色，我想在总览看到当前库存、安全库存线与低库存置顶标记，以便快速识别风险。
20. 作为学生，我想看到安全库存线，以便理解某耗材为何被标红。
21. 作为教师/班委，我想看到"耗材总类数 / 低库存数 / 今日领用笔数"指标卡，以便快速掌握全局。
22. 作为教师/班委，我想按耗材、时间、领用人、流水状态筛选记录并导出 CSV，以便盘点核对。
23. 作为学生，我想只看到本人的领用流水，以便自查。
24. 作为任一角色，我想库存为 0 的耗材被标记"缺货"，以便优先补货。

### 智能补货
25. 作为教师/班委，我想打开建议页自动巡检并按"紧急→一般→观察"排序展示卡片，以便优先处理最紧急缺料。
26. 作为教师/班委，我想每张卡片展示缺口、净消耗、日耗速率、可支撑天数、建议补货量与判断依据，以便理解建议。
27. 作为教师/班委，我想大模型超时或不可用时看到规则模板文案而非报错，以便演示稳定。
28. 作为教师/班委，我想正常库存的耗材不产生建议且不调用大模型，以便控制成本与延迟。
29. 作为班委，我想处置建议时录入实际入库数量并自动增加库存与留痕，以便完成补货闭环。
30. 作为教师/班委，我想观察档包含趋势预警（环比上升 50%，前 7 天为 0 视为上升），以便发现用量突变。
31. 作为教师/班委，我想安全库存线为 0 的耗材不参与巡检，以便按需关闭预警。

### 统计与审计
32. 作为教师/班委，我想近 7/30 天消耗按"领用 − 红冲"的净消耗统计（负值截断为 0），以便撤销后数据正确。
33. 作为教师/班委，我想操作日志覆盖登录、领用、撤销、档案变更与建议处置，以便责任可追溯。
34. 作为教师/班委，我想通过流水与操作日志反推任一时点的库存，以便对账。

### 工程与交付
35. 作为开发者，我想 CodeArts 流水线三阶段（前端构建 → pytest → 镜像构建发布）可一键执行且镜像可回滚，以便满足赛事工程要求。
36. 作为演示者，我想本地零 Docker 启动系统（venv + 本地 MySQL + Vite），以便云端故障时兜底。
37. 作为演示者，我想 seed 数据包含三级场景（1 缺货 + 1 低库存 + 1 趋势上升），以便 3 分钟演示闭环完整。

## Implementation Decisions

### 模块划分
- 后端模块：auth（登录/JWT/鉴权依赖）、users（用户管理）、consumables（档案）、requisitions（批量领用与撤销）、inventory（巡检、建议与处置入库）、agent（规则引擎纯函数）、llm（大模型适配器）、consumption（净消耗统计）、logs（操作日志）、common（错误处理、分页、CSV 导出）
- 前端页面：登录、库存总览、档案管理、领用登记、记录查询、补货建议、消耗汇总、操作日志、用户管理；路由守卫按角色加载菜单

### 数据模型（四张表）
- `users`：id、account、password_hash、name、role（teacher/admin/student）、class_id、status（启用/禁用）、created_at
- `consumables`：id、name、spec、unit、location、safety_stock、current_stock、class_id、status（启用/停用）、created_at、updated_at
- `requisitions`：id、consumable_id、user_id、quantity、stock_after（领后剩余快照）、type（领用/红冲）、status（有效/已撤销）、reversal_of（红冲关联原流水）、reversal_reason、class_id、created_at、remark
- `operation_logs`：id、operator_id、role、action、target_type、target_id、before_value、after_value、remark、created_at

### 库存与事务规则
- 当前库存只允许三条变更路径：领用扣减、撤销回加、建议处置入库；无直接编辑入口
- 扣减使用条件原子更新（`current_stock = current_stock - ? WHERE id = ? AND current_stock >= ?`），批量领用整单在一个事务内逐行扣减并写流水，任一行失败全部回滚
- 撤销与入库均为单事务：库存变更 + 流水/日志 + 状态标记必须同时成功
- 撤销原因必填；教师/班委可撤销，学生不可；不设时间窗口

### Agent 规则引擎（纯函数）
- 输入：当前库存 C、安全库存线 S、近 7 天净消耗 Q7、再前 7 天净消耗 Qprev7
- 净消耗：Q = max(Σ领用 − Σ红冲, 0)（按统计窗口）
- 指标：G = max(S − C, 0)；r = Q7 ÷ 7；D = r > 0 ? C ÷ r : +∞
- 分级（顺序判定，首个命中定档）：紧急 = C=0 或 D≤1 或 C<S×30%；一般 = C<S 且 D≤3；观察 = C<S 且 D>3，或 C≥S 且 Q7 ≥ 1.5×Qprev7（Qprev7=0 且 Q7>0 视为上升）；其余为正常
- S=0 的耗材跳过巡检
- 建议补货量：R = ceil(G + r×7)；r=0 且 G>0 时 R=G；观察档因趋势触发（C≥S）时 R=ceil(r×7)；R 下限 0

### 大模型适配
- 适配器接口：输入结构化的耗材指标与分级结果，输出 2–4 句中文判断依据；DeepSeek 为默认实现，接口保留切换华为云盘古
- 仅对非"正常"档调用；单次超时 3 秒，超时/异常回退规则模板文案
- 巡检结果按耗材缓存 10 分钟；不保存历史巡检快照；密钥由环境变量注入

### 认证与会话
- bcrypt 哈希密码；PyJWT 签发，JWT 写入 httpOnly Cookie（SameSite=Lax），有效期 8 小时
- 鉴权依赖从 Cookie 解析 JWT 并校验角色；越权返回 403；未登录 401

### API 资源（概要）
- `/api/v1/auth`：login、logout、me
- `/api/v1/users`：班委新增学生、启停用；列表
- `/api/v1/consumables`：CRUD、停用、列表（含安全库存状态）
- `/api/v1/requisitions`：批量创建（≤5 行）、查询（筛选/分页）、撤销、CSV 导出
- `/api/v1/inventory`：建议列表（巡检）、重新巡检、处置（入库数量+备注）
- `/api/v1/consumption`：净消耗汇总（7/30 天）、日均速率
- `/api/v1/logs`：操作日志查询（教师/班委）
- 统一响应信封：成功返回数据，失败返回错误码与中文提示；分页统一 limit/page

### 前端行为
- Element Plus 组件库；Axios 拦截器统一处理 401（跳登录）与 403（提示无权限）
- 领用表单支持动态添加行（最多 5 行），提交中禁用按钮
- 建议卡片以红/黄/蓝标签区分三级；学生角色不渲染补货建议、档案、用户管理、日志入口

### 部署与流水线
- 云端：单台华为云 ECS（2C4G）+ Docker Compose（nginx:alpine 托管前端并反代 /api、python:3.12-slim 运行 FastAPI、mysql:8.0），公网 IP + HTTP
- 本地：Python venv + `requirements.txt` + 本地 MySQL 8.0 + Vite dev server，零 Docker
- CodeArts 流水线三阶段：前端构建（node:22-alpine）→ pytest（含覆盖率）→ 镜像构建推送 SWR 并发布 ECS；镜像携带版本标签支持回滚

### 配置
- pydantic-settings 读取 `.env`：数据库连接、JWT 密钥、LLM 供应商与密钥、时区 Asia/Shanghai
- 密钥不进入仓库、不写入日志；`.env.example` 仅提供占位

## Testing Decisions

**好测试的定义**：只断言外部行为——HTTP 状态码与响应字段、纯函数返回值；不 mock 内部实现、不测试私有函数、不依赖执行顺序之外的实现细节。

**Seam 1（主）：HTTP API**
- 工具：pytest + httpx TestClient；fixture 建 SQLite in-memory 库并注入种子数据与三角色会话
- 覆盖模块：auth/users（登录、越权 403、班委仅能管学生）、requisitions（批量原子、一行不足整单回滚、撤销红冲、二次撤销拒绝、30 天补录边界）、inventory（巡检输出、处置入库、正常档不出卡）、consumption（净消耗含撤销、7/30 天切换）、logs（写操作留痕）
- 断言外部契约，不检查数据库内部实现（必要时通过 API 读取验证）

**Seam 2（辅）：规则引擎纯函数**
- `compute_tier(C, S, Q7, Qprev7)` 与 `compute_replenishment_quantity(G, r, tier)` 直接单测
- 参数化边界表：S=0 跳过、C=0 紧急、D=1 与 D=3 边界、C < S×30%、趋势 50% 恰好命中、Qprev7=0 且 Q7>0、r=0 且 G>0、ceil 取整（如 12.2→13）

**测试数据**
- 复用 seed 脚本的三级演示场景（1 缺货 / 1 低库存 / 1 趋势上升），API 测试另建独立 fixture 数据
- 时间相关断言固定 Asia/Shanghai 自然日口径

**前端**
- 不写自动化测试；由 3 分钟演示脚本人工冒烟（登录→建档→批量领用→撤销→预警→建议→处置→日志）

**数据库差异说明**
- 测试用 SQLite in-memory，生产 MySQL 8.0；库存条件更新语句在两方言下语义一致，唯一差异是 MySQL 行锁——并发正确性由条件更新保证，不依赖方言特性

## Out of Scope

- 外部推送（邮件 / 微信 / 短信 / App 通知）；"提醒"仅指页面预警与建议卡片
- 登录失败锁定、验证码、密码找回、自助注册
- 数据备份、容灾与生产级高可用
- 采购订单、供应商、物流、财务结算
- 扫码枪、RFID、电子秤等硬件集成
- 微信小程序、原生 App、桌面客户端
- 多级审批流
- 耗材批次、保质期、条码、包装规格
- 多班级管理界面、班级切换、班级管理员角色（仅保留 class_id 数据维度）
- 跨学期库存结转与折旧对冲（历史可查，不做自动账务）
- 前端自动化测试
- 域名与 HTTPS（公网 IP + HTTP 演示）
